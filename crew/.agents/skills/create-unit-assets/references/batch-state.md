# 배치 상태·비용·재개 계약

이 문서는 실행자가 작성하는 기록의 계약이다. 자체 실행 엔진이나 이미 실행된 상태를 뜻하지 않는다. 기존 manifest 형식은 보존하고 추가 기록에서 연결한다.

## 기록 소유권

- 메인: `coordinator/batches/<batch_id>/batch.json`, `coordinator/ships/<asset_id>/pipeline.json` 또는 `coordinator/monsters/<asset_id>/pipeline.json`.
- 제작자: 자기 `ships/` 또는 `monsters/` 아래 concept/multiview 기록. 메인은 shared 인계본의 버전·해시와 검수 응답을 자기 pipeline에 연결하며 제작자 원본을 열거나 수정하지 않는다.
- `batch_id`, `asset_id`, 버전은 단일 경로 구성요소로 제한한다. 구분자·`..`·절대 경로를 거부한다. 경로의 실제 대상과 reparse point를 확인하고 링크로 영역 밖에 접근하지 않는다.

| 기록 | 필수 정보 |
| --- | --- |
| batch | 스키마 버전, batch ID, 요청 유닛/종료 단계, 카탈로그·스타일 버전/해시, 파일럿 ID, 요청·권한 범위, 비용 한도/단위, 공통 기준 버전, 자산별 pipeline 위치/상태 |
| pipeline | asset ID·종류, source 출처/반입본/해시/atlas 영역, 사용자 변경 조건, 단계별 입력·출력 버전/해시, 호출자·담당자, 검수 응답, 비용·횟수, 최종 패키지와 종료 사유 |
| stage | 단계명, 상태, 입력 해시 집합, 실제 파일/해시, 실제 reviewer ID·판정·대상 해시, 사용자 선택 상태, 이전 단계 연결 |
| attempt | 호출 전 고정 request ID·입력 해시·견적·설정·시각, 제출 상태, 반환 task ID, 실제/미확정 비용, 생성·재사용·보정 구분 |

배치 합계는 자산 기록의 합계이며 같은 호출을 중복 계상하지 않는다. 실행·검수 기록을 먼저 안전하게 저장하고 배치 요약을 갱신한다. 중단 후 불일치하면 원본 attempt 기록으로 합계를 복구한다.

## 승인과 상태

단계는 `source → concept → multiview → model → package`다. 실행 상태는 `pending`, `running`, `completed`, `stale`, `blocked_input`, `blocked_role`, `blocked_tool`, `blocked_evidence`, `blocked_budget`, `validation_failed`, `needs_changes`, `stopped_by_user`, `submission_unknown`, `iteration_limit_reached`, `repeated_issue`로 구분한다. 디렉터 판정(`approved_for_next_stage|changes_requested|blocked_missing_evidence`)과 사용자 선택(`pending|selected|exception`)은 실행 상태와 별도 필드다.

- 아트 단계의 `completed`는 실제 대상 파일 해시와 연결된 독립 승인이 있어야 한다. 컨셉은 한 장, 멀티뷰는 재사용 방향을 포함한 네 파일 전체 세트, 모델은 최종 모델과 그 실제 렌더가 대상이다.
- 패키지 완료는 최종 모델 승인 + 정적 납품 검증 통과다. 요청한 종료 단계까지만 완료를 판단한다. 컨셉까지만 요청한 실행을 패키지 완료로 표시하지 않는다.
- 상위 입력이 바뀌면 그 입력에 의존하는 하위 단계를 `stale`로 표시한다. 기존 파일·승인 기록은 삭제하지 않는다. 영향 없는 방향을 재사용하더라도 새 멀티뷰 세트 검수는 필요하다.
- `approved` 파일명, 서비스 `success`, 사용자 보관 선택, 자기 검수는 독립 승인의 대체가 아니다. 사용자 예외는 결함·버전·범위를 따로 기록하고 원래 디렉터 판정을 바꾸지 않는다. 예외 결과는 기본의 승인 완료와 구분해 납품한다.

## 미완료 상태 적용

- 실제 후보/검수 자료가 빠져 보완을 기다리면 `blocked_evidence`다. 디렉터의 `blocked_missing_evidence`는 별도 판정 필드에 보존한다.
- 필수 수정 판정 후 다음 수정 전에는 `needs_changes`다. 수정을 시작하면 `running`, 한도에 이르면 구체적인 한도/반복 종료 상태를 사용한다.
- 엔진·GPU·도구가 없어서 검증을 못 하면 `blocked_tool`, 실행한 임포트·리소스·재배치 검사가 실패하면 `validation_failed`다. 동시에 발생한 다른 사유도 종료 사유 목록에 모두 남긴다.
- 사용자가 미승인 후보를 보관만 하고 제작 종료하도록 명시하면 `stopped_by_user`다. 보관 선택과 실제 디렉터 판정을 보존하며 추가 생성하지 않는다.
- 위 상태를 `completed`로 바꾸려면 누락된 증거/도구, 필수 수정 또는 사용자 종료 범위를 해결하고 해당 단계의 완료 조건을 실제로 충족해야 한다.

## 한도와 제출

- 기본 유닛별 한도: 컨셉 최초+수정 합계 3개, 멀티뷰 최초+수정 2회/총 12장, 모델 최초+필수 수정 2회/유료 호출 합계 3건. 모델 국소 보정과 재생성은 같은 수정 2회 안에서 선택한다. 패키지 기술 수정은 최초+수정 2회이며 모델 형상·재질 수정이 포함되면 모델 수정 한도도 소비한다.
- 같은 필수 결함이 두 수정에도 남으면 `repeated_issue`, 그 외 횟수 소진은 `iteration_limit_reached`다. 단계·역할·배치 변경, 도구 실패로 한도를 초기화하지 않는다. 별도 사용자 추가 회차 승인이 있을 때만 이전 사용량을 보존한 채 상한을 확장한다.
- 첫 유료 제출 전에 실제 입력을 고정한 dry-run과 현재 단가/견적을 준비해 배치 전체 지출 한도를 정한다. 이미 지정한 한도는 다시 묻지 않는다. 계정 잔액은 한도가 아니다. 통화와 크레딧을 임의 환산하지 않는다.
- 확인된 지출 + 진행 중/불명확 호출의 예약 상한 + 다음 호출 견적이 한도 이내일 때만 제출한다. 요금에 상한을 둘 수 없으면 그 호출을 보류한다. 공급자가 실제 비용을 주지 않으면 `unknown`을 유지하고 예약액을 임의로 해제하지 않는다. 무료/구독 포함 이미지 호출과 별도 유료 호출도 구분한다.
- 제출 전에 attempt를 저장하고 반환 task ID를 즉시 저장한다. 응답 유실·타임아웃이면 `submission_unknown`으로 두고 기존 ID·요청 기록·서비스 작업 목록을 조회한다. 제출되지 않았다는 근거 없이 자동 재제출하지 않는다. 불명확 비용을 예약한 채 다른 준비 작업은 진행할 수 있다.

## 재개 순서

1. batch 요청 범위와 각 attempt/task ID를 읽고 진행 중 작업을 먼저 조회한다.
2. 실제 파일과 입력/출력 해시, 최종 판정의 연결을 확인한다. 누락된 검수 증거부터 복원하고 새 생성으로 우회하지 않는다.
3. 누적 비용·한도·사용한 수정 횟수를 복구한다. 승인 완료 유닛은 유지하고 미완료/유효하지 않은 단계부터 계속한다.
4. 전체 신규 배치에서 파일럿이 요청 종료 단계까지 미완료면 나머지 유닛의 생성은 보류하되 원본 확인·브리프 준비는 가능하다. 선택 배치에 없는 파일럿 유닛을 추가하지 않는다. 컨셉/멀티뷰/모델에서 종료하는 배치에 패키지 검증을 요구하지 않는다.
5. 모델 아트 승인 뒤 엔진이 없거나 GPU 검증을 못 하면 패키지를 미검증으로 두고 확보한 GLB와 다음 의존성을 보고한다. headless 임포트만으로 시각 검증을 통과시키지 않는다.

## 전체 비교와 배치 완료

복수 유닛 요청은 요청 종료 단계의 실제 결과로 전체 비교를 수행한다. `batch_review`에 공통 기준 버전, 비교한 모든 asset ID·단계·파일 해시, reviewer ID·판정·피드백을 저장한다. 단일 유닛 요청은 `not_applicable`로 기록한다. 전체 완료는 요청 유닛이 모두 요청 단계까지 완료됐고 복수 유닛의 비교 검수도 승인됐을 때다. 개별 패키지가 모두 완료돼도 계열 일관성에 필수 수정이 남으면 배치 실행 상태는 `needs_changes`, 디렉터 판정은 `changes_requested`로 보고하고 개별 승인 기록을 삭제하지 않는다. 수정 대상과 예산 잔여를 확인한 뒤 영향을 받는 단계부터 재개한다.
